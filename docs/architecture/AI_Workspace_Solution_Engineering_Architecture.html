View 01

End-to-end solution architecture

Implemented — phase 1Implemented — phase 2Migrated in productionAwaiting deployGemini: future
  1. The launcher and workspace render only when the app layout finds users.role = 'admin'. The browser talks only to same-origin /api/admin/ai/workspace routes and holds no key.
  2. Every route starts with workspaceAdmin(), which re-reads the role from the database and answers 404 to everyone else.
  3. The admin's id is the only identity the runtime receives; every data-layer statement is scoped by it.
  4. The runtime assembles the model request from five layers only and hands turns and parts to the provider seam.
  5. src/lib/ai/claude.ts is the one file that uses Anthropic's SDK. It streams from the Messages API and uploads attached PDFs and images to the Files API once.
  6. Text streams back to the browser as NDJSON and is saved to the reply's row as it arrives.
View 02

Backend functional block architecture

Routes and runtime — phase 2Data layer — phase 1

Conventions every block follows

  • The admin's user id is the first argument of every data-layer function; missing and foreign rows are indistinguishable (null, false or 404).
  • Multi-statement writes run in one transaction(), locking the row they change with FOR UPDATE.
  • Refusals are ApiErrors with safe English sentences, translated at the edge by localiseError; anything unrecognised becomes the generic message.
  • No block logs content: unexpected errors are logged as a name and a code only.

What the data layer cannot see

  • No SQL naming a RichHabit data table; no import of analytics, auth, the store or domain modules (tests: ai-workspace-boundaries, ai-workspace-runtime-boundaries).
  • No credential or process.env read; configuration arrives through env.ts getters.
  • Only src/lib/aiWorkspace names the ai_ tables.

For review

Findings: code against the proposal

Where the implementation differs from the approved proposal

  1. M-1The proposal kept the hourly limit and concurrency in memory. Both limits are counted from the database, and one reply at a time is held twice: a synchronous in-process slot and the data layer's streaming check.
  2. M-2The proposal recovered stale replies when a conversation opens. The data layer also recovers before every reply, Continue and Retry, and the conversation view recovers a reply no request owns after 20 seconds instead of 15 minutes.
  3. M-3The proposal offered Regenerate on the last reply. Retry/Regenerate is offered on every visible answer the lifecycle allows; retrying an earlier message sends history only up to that message.
  4. M-4Text files are not uploaded to the Files API; they are sent inline as text documents. PDFs and images use stored copies, with a one-request inline fallback when an upload fails.
  5. M-5The 200,000-token context ceiling is configuration only. History is trimmed to the 150,000 target by estimate; a request still too long fails as context_too_long with a clear message.
  6. M-6The upload notice words the retention point as "not covered by zero data retention" and adds that Anthropic keeps files until they are deleted.

Behaviour the implementation has that the proposal did not describe

  1. B-1An archived conversation refuses send, Continue, Retry and uploads; an archived project refuses new chats and library uploads, while its existing chats still work.
  2. B-2A client id reused in a different conversation is refused (409) rather than returning the other conversation's rows.
  3. B-3A conversation with only files is titled from the first file's name; an edited title is never overwritten.
  4. B-4De-duplication runs before the quota check, so re-uploading stored bytes succeeds even when storage is full.
  5. B-5Removing a chip before sending deletes that upload outright; files already carried by a message are left alone.
  6. B-6Stop also ends a reply that no request is writing, keeping the text saved so far.
  7. B-7The deletion summary counts live files, while permanent delete reports all files including tombstones, so the second number can be higher.
  8. B-8Migration step 8 creates a missing index on an existing table but counts only new tables, so its "Nothing to do" can follow an index repair.

Risks and limits to carry forward

  1. R-1The reply slot and orphan recovery assume one server instance, which is RichHabit's Render setup. Several instances would need the slot in the database. During a deploy overlap, a reply still running on the old instance can be marked interrupted by the new one.
  2. R-2Deleting a whole account cascades its workspace rows without collecting Files API copies, so those remote copies are not deleted.
  3. R-3Remote copy deletion is best effort with no retry queue; failures are logged as codes.
  4. R-4Uploaded files are type-checked, not scanned for malware; they are served sandboxed and only to their owner.
  5. R-5Render did not auto-deploy recent releases; deploys are manual.
